# Gush Ball

Website for the club: team pages, schedule/standings, scores, and (later) stats — scraped from
[ibasketball.co.il](https://ibasketball.co.il) with admin review, plus manual admin management.

## Stack

- **Backend**: Python, FastAPI, SQLAlchemy, Alembic, PostgreSQL
- **Frontend**: Vue 3 (JS, not TS), Vite, Tailwind CSS v4, Vue Router
- **Auth**: single admin role, session cookie (no fan/player accounts)

## Local setup

### 1. Database

```
docker compose up -d
```

### 2. Backend

```
cd backend
cp .env.example .env
uv run alembic upgrade head
uv run python scripts/create_admin.py <username> <password>
uv run uvicorn app.main:app --reload
```

Runs on http://localhost:8000. Tests: `uv run pytest`.

### 3. Frontend

```
cd frontend
npm install
npm run dev
```

Runs on http://localhost:5173, proxying `/api/*` to the backend. Tests: `npm run test`.

## Deployment

Host: **Render**. `render.yaml` (repo root) is the source of truth for the whole topology — one
Postgres database plus the backend and frontend services — declared as a Blueprint instead of
three dashboard configs.

- The **frontend** static site proxies `/api/*` to the backend via a Render rewrite route (see
  `render.yaml`), so the frontend's existing relative, cookie-bearing `fetch('/api/...')` calls
  work unchanged in production — same-origin from the browser's point of view, no CORS preflight,
  no cross-site cookie config needed.
- The **backend** runs `alembic upgrade head` automatically on every boot (its `startCommand`), so
  migrations don't need a separate manual step or CI job.
- CI (`.github/workflows/ci.yml`) has a `deploy` job that fires Render's deploy hooks after the
  `backend` and `frontend` test jobs pass on a push to `master`. `render.yaml` sets
  `autoDeploy: false` on both services so Render doesn't also deploy straight off the git push
  before CI has verified it.

**Env vars — blueprint-generated vs. secret:**

| Var | Source |
| --- | --- |
| `DATABASE_URL` | generated by Render from the `gush-ball-db` database (`fromDatabase`) |
| `SESSION_SECRET` | generated by Render (`generateValue: true`) |
| `CORS_ORIGINS` | committed placeholder in `render.yaml`, needs a real value (see below) |
| `OBJECT_STORAGE_*` (6 vars) | `sync: false` — entered by hand in the Render dashboard, never committed |

**One-time manual setup** (account/credential work an automated change can't do):

1. Create a Render account and connect it to this repo.
2. Create a Blueprint instance from `render.yaml` in the Render dashboard — this provisions the
   Postgres DB and both services.
3. Fill in the six `OBJECT_STORAGE_*` secrets in the Render dashboard (needs the R2/S3 bucket from
   issue #6 to exist first).
4. Copy the two per-service Deploy Hook URLs Render generates into this repo's GitHub Actions
   secrets: `RENDER_BACKEND_DEPLOY_HOOK`, `RENDER_FRONTEND_DEPLOY_HOOK`.
5. Patch up the circular URL reference once real `*.onrender.com` URLs are assigned: set the
   backend's `CORS_ORIGINS` to the frontend's real URL, and the frontend rewrite route's
   `destination` to the backend's real URL (in the dashboard or by editing `render.yaml` and
   redeploying), since each only exists after the other's first deploy.
6. **Upgrade the Postgres database off the free plan before it's deleted.** Render's free Postgres
   plan expires 30 days after creation, then is deleted ~14 days after that if not upgraded — the
   database is gone (~44 days total) unless it's upgraded to a paid plan before then.

## Project phases

1. **Phase 1** (current): manually-populated public site (teams, players, schedule, standings,
   scores) + basic admin CRUD. Hebrew/RTL only. Dark/light toggle.
2. **Phase 2**: scraper (standings + schedule/results + opponent logos from ibasketball.co.il)
   into a pending-review admin queue, with manual-override protection against re-scrape clobber.
3. **Phase 3**: statistics (design TBD), social media embeds, dynamic per-team color theming.
